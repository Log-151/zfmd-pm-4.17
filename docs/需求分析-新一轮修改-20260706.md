> 基于用户原始需求，逐条深度分析、完善拆解为可执行的标准开发提示词。
> 日期：2026-06-16

## 2026-07-13 追加需求评估（基于 17.0.1.8.4 现状）

### 一、项目现状与本轮结论

本项目是基于 Odoo 17 的单体业务模块 `zfmd_pm`，合同台账、服务记录、开票登记、应收计划、回款登记、开工申请和项目管理之间通过合同编号、`contract_id` 以及 `sync_engine` 联动。此前几轮修改已经落地了本轮需求的部分基础能力：

- 服务记录已经能够按“场站名称”从已确认的合同中取最新服务结束日期，但尚未把“省份”纳入匹配条件。
- 开票登记已经存在 `receivable_plan_id`，当前是一条开票记录对应一条应收计划；应收计划通过 `invoice_record_ids` 反查开票记录。
- 应收计划中的“已开票金额”目前同时显示在列表和表单中。
- 开工申请当前按“合同编号倒序、记录 ID 倒序”排列，不是按开工申请编号排列。

本轮四项需求的总体判断如下：

| 需求 | 当前实现 | 改造级别 | 主要影响 |
|---|---|---:|---|
| 服务合同到期时间按场站名称＋省份取最新 | 已按场站名称取最新 | 中 | 模型、合同联动、导入、历史数据重算、测试 |
| 一条开票关联多条同合同应收计划 | 当前只能单选一条 | 高 | 关系字段、界面、同步逻辑、导入、数据迁移、测试 |
| 隐去应收计划“已开票金额” | 列表和表单均显示 | 低 | 视图；模型字段可暂时保留 |
| 开工申请按申请编号倒序 | 当前按合同编号倒序 | 低 | 模型默认顺序、列表默认顺序、测试 |

> 本节中的方案取代本文旧“提示词7（服务到期时间仅按场站取最新）”和“提示词14（开票单选应收计划）”。实施时不得继续沿用旧提示词中的单字段匹配和 `Many2one` 设计。

### 二、需求一：服务记录的服务合同到期时间

#### 2.1 明确后的业务规则

对每一条服务记录，以该记录的：

1. `site_name`（场站名称）；
2. `province_name`（省份/省区）

为联合匹配键，在合同台账 `zfmd.contract` 中查找对应条目；仅纳入已有架构中可参与业务联动的“已确认”合同，并排除 `service_end_date` 为空的合同。按 `service_end_date desc, id desc` 排序，取第一条的服务结束日期，写入服务记录的 `service_end_date`（服务合同到期时间）。

等价规则：

```text
服务合同到期时间 = MAX(
  合同台账.服务结束日期
  WHERE 合同台账.场站名称 = 服务记录.场站名称
    AND 合同台账.省份 = 服务记录.省份
    AND 合同台账.录入状态 = 已确认
)
```

若场站名称或省份任一为空，或没有找到满足条件且服务结束日期非空的合同，结果应为空，不应退化为只按场站匹配，否则同名场站可能串用其他省份的日期。

#### 2.2 现有代码差距

- `models/service_record.py` 的 `_latest_service_end_date_from_site_name()` 只接收 `site_name`，查询域缺少 `province_name`。
- `create()`、`write()`、`onchange` 和 `_compute_service_end_date_from_site()` 都只围绕场站触发；用户修改省份时不会可靠重算。
- `models/sync_engine.py` 在合同变更后只处理与当前合同 ID/合同号关联到的服务记录，不能完整覆盖“未直接关联合同、但场站名称＋省份相同”的服务记录。
- 导入向导虽然已经用省份辅助查找唯一合同，但服务记录最终保存时，模型层仍会按“仅场站”覆盖导入日期，规则不一致。

#### 2.3 推荐实现

1. 将辅助方法改为 `_latest_service_end_date_from_site_province(site_name, province_name)`，统一做空值处理和字符串去首尾空格。
2. 所有入口统一调用这一方法：
   - 选择关联合同时的 `onchange`；
   - 新建服务记录；
   - 修改 `site_name`、`province_name` 或 `contract_id`；
   - 合同的场站、省份、服务结束日期或确认状态变化后。
3. `sync_engine.sync_contracts()` 应按“场站名称＋省份”查找全部受影响服务记录并重算，而不是只查直接关联当前合同的记录。
4. 合同若从旧场站/旧省份改到新值，应同时重算旧联合键和新联合键下的服务记录，避免旧分组仍保留过期结果。可在 `contract.write()` 前保存旧联合键，通过上下文传给同步引擎，或增加一个按联合键批量重算的方法。
5. 新增迁移脚本，对全部未删除服务记录按新规则重算；迁移应幂等，重复执行结果一致。

#### 2.4 验收场景

- 同一场站、同一省份有三份合同，结束日期分别为 2026-06-30、2026-12-31、空：取 2026-12-31。
- 两个省份存在同名场站：服务记录只能使用本省合同日期。
- 最新日期所在合同未确认：不参与计算，取其余已确认合同中的最新日期。
- 修改服务记录省份后立即重算。
- 修改合同服务结束日期、场站、省份或确认状态后，所有相同联合键的服务记录均同步更新。
- 场站或省份为空、没有匹配合同、所有匹配合同日期均为空：服务合同到期时间为空。

### 三、需求二：一条开票记录关联多条应收计划

#### 3.1 数据模型调整

将开票模型当前的单选字段：

```python
receivable_plan_id = fields.Many2one("zfmd.receivable.plan", ...)
```

升级为多选字段，建议使用新字段名以清楚表达复数关系：

```python
receivable_plan_ids = fields.Many2many(
    "zfmd.receivable.plan",
    "zfmd_invoice_receivable_plan_rel",
    "invoice_record_id",
    "receivable_plan_id",
    string="对应应收计划",
)
```

应收计划侧的反查字段同步改为使用同一关系表的 `Many2many`。原有 `receivable_plan_id` 不建议直接原地改类型；应先新增关系表、迁移旧值、切换代码和视图，验证后再决定是否删除旧列。这样回滚和核对历史关系更安全。

#### 3.2 选择交互

- 用户应先选择关联合同，再选择应收计划。
- 应收计划选择域必须使用稳定的关系字段：`[('contract_id', '=', contract_id)]`，保证候选项与开票记录合同一致。
- 使用 Odoo 标准多对多选择列表，点击“添加”后在列表中勾选一条或多条应收计划并确认；候选列表至少展示“应收款项名称、应收金额、应收时间、场站、状态”，以便区分同合同下的多条计划。
- 已选择项应在表单中以列表或标签形式可见并可移除。数据量较多时不建议使用一次性渲染全部数据的 `many2many_checkboxes` 小部件。
- 服务端必须增加约束：所有已选应收计划的合同必须与开票记录合同一致。不能只依赖前端 domain，因为导入、接口或脚本可以绕过界面。
- 合同变更后，应清除不属于新合同的已选应收计划，并提示用户重新选择；更稳妥的方式是在已有选择时阻止直接换合同，要求先清空应收计划。

#### 3.3 金额规则边界

业务已确认：一张发票关联多条应收计划时不分摊发票金额。应收计划会随实际开票调整；只要关联的有效开票记录存在开票时间，该应收计划即认定为已经开具全额发票。

确定后的规则：

- 参与认定的开票记录必须已确认、未删除、未作废，且 `invoice_date` 非空。
- 一张开票关联多条应收计划时，每条计划的 `actual_invoice_date` 均取关联有效发票中的最新开票日期。
- 每条应收计划均独立认定为全额开票，不比较发票金额与应收计划金额，也不在计划之间分摊 `invoice_amount`。
- 模型内部如需保留 `invoiced_amount` 兼容字段：存在有效带日期发票时等于该计划的 `receivable_amount`，否则为 0；该字段仍按本轮要求从界面隐去。
- 同一计划关联多张发票时只更新实际开票日期，不累加成超过应收金额的“已开票金额”。
- 清除发票日期、取消关联、发票作废、删除或变为未确认后，应重新计算；没有其他有效发票时，计划恢复为未开票。

#### 3.4 现有联动与导入改造

- `sync_engine.refresh_from_invoices()` 中的判断由 `invoice.receivable_plan_id == receivable` 改为 `receivable in invoice.receivable_plan_ids`。
- 对未选择任何应收计划的历史/导入开票，是否继续按“同合同全部应收计划”回写日期需要收紧。推荐取消该兜底，避免一张未明确关联的发票把同合同所有应收计划都标记为已开票；历史数据应通过迁移保留已有单选关系。
- `invoice_import_wizard.py` 当前通过“合同＋应收款项名称”只查一条计划。导入文件若仍只有一个应收款项名称，可迁入多选字段中的单个值；若一个单元格允许多个名称，需要明确分隔符并逐项精确匹配，任一名称不唯一时应给出警告，不可静默取最新一条。
- 开票表单带值应以合同为主。多选应收计划不自动计算或分摊开票金额，`invoice_amount` 继续记录发票自身实际金额。
- `views/search_views.xml` 的开票搜索视图当前直接引用 `receivable_plan_id`，需切换为多选字段，并验证按任一关联应收计划搜索的行为。
- `models/export_mixin.py` 的开票导出列当前直接导出单个 `receivable_plan_id`，需改为输出所有已选应收计划的可读名称，建议用“；”拼接，不能导出内部数据库 ID。
- 全项目搜索旧字段名，确保模型、视图、搜索、同步、导出、导入和测试中不再误用 `receivable_plan_id`；仅迁移兼容代码可以暂时保留旧字段引用。

#### 3.5 历史数据迁移

新增版本迁移（建议升至新的次版本）并执行：

1. 创建 `zfmd_invoice_receivable_plan_rel` 关系表及唯一约束；
2. 将每条开票记录原 `receivable_plan_id` 非空值迁为一条关系表记录；
3. 校验迁移前后“有应收关联的开票记录数”和关系数；
4. 完成关系复制后再由 Odoo 升级过程清理旧字段元数据和旧列；
5. 迁移脚本使用 `NOT EXISTS` 或等价逻辑，确保可重复执行。

#### 3.6 验收场景

- 选择合同 A 后，只能勾选合同 A 下的多条应收计划。
- 一张开票可保存 1 条、2 条或更多应收计划；取消其中一条后关系正确更新。
- 通过导入或服务端写入合同 B 的应收计划到合同 A 的开票时，系统阻止保存并给出明确提示。
- 历史单选数据升级后仍保留原关联。
- 一张未作废发票关联两条计划，两条计划的实际开票时间都正确更新；发票作废后重新计算。
- 两条计划分别按各自应收金额认定为全额开票，不对发票金额做分摊或累计。

### 四、需求三：应收计划隐去“已开票金额”

#### 4.1 推荐范围

本轮按“隐去”理解为只移除用户界面展示，不立即删除数据库/模型字段：

- 从 `views/receivable_plan_views.xml` 的列表视图移除 `invoiced_amount` 列；
- 从表单视图移除 `invoiced_amount` 字段；
- 检查搜索、透视、图表、通用导出和自定义导出字段配置，确保没有其他入口继续展示该字段。

模型字段暂时保留用于兼容旧调用，并按“有有效开票时间即等于应收金额”的规则计算；用户界面不再展示。

#### 4.2 验收标准

- 应收计划列表、表单、搜索、透视、图表和标准导出入口均不显示“已开票金额”。
- 升级后历史应收计划可正常打开，不因隐藏字段或关系迁移报错。

### 五、需求四：开工申请按申请编号倒序

#### 5.1 现有差距与修改点

当前存在两处按合同编号排序的定义，必须同时修改，否则模型默认顺序和列表顺序会不一致：

- `models/project_start.py`：`_order = "display_contract_no desc, id desc"`
- `views/project_start_views.xml`：`default_order="display_contract_no desc, id desc"`

统一修改为：

```text
name desc, id desc
```

其中 `name` 即“开工申请编号”，`id desc` 用于编号相同时提供稳定次序。

#### 5.2 排序风险说明

数据库对字符字段执行的是字典序倒序。如果开工申请编号格式固定、数字部分等长（例如 `KG-2026-0010`），结果符合业务直觉；如果存在 `KG-9`、`KG-10` 这种数字不补零的混合格式，字符排序会出现 `KG-9` 排在 `KG-10` 前。实施前应抽查生产编号格式；若格式不固定，需要新增可存储的数值排序键，而不能只改 `name desc`。

#### 5.3 验收标准

- 打开开工申请列表时，默认按开工申请编号倒序。
- 从其他动作、合同快捷入口或回收站打开记录时，未显式指定其他顺序的场景也遵循模型默认顺序。
- 相同编号时按新建记录 ID 倒序，分页前后顺序稳定。

## 需求二：人工修改被自动计算覆盖（项目管理合同执行情况）

### 问题分析

查看 [sync_engine.py:286-292](addons/zfmd_pm/models/sync_engine.py#L286-L292)，`_refresh_project` 方法中每次联动触发时都会无条件覆盖 `contract_execution_status`：

```python
if project.service_end_date:
    execution_status = "服务中" if project.service_end_date >= today else "服务结束"
elif acceptance_voucher == "有":
    execution_status = "已完工"
elif arrival_voucher == "有":
    execution_status = "施工中"
else:
    execution_status = "未开工"
```

然后在 line 310 无条件写入：
```python
"contract_execution_status": execution_status,
```

**根因**：没有"手动修改标记"机制。用户手动修改的值在下次任意联动触发（回款、开票、应收变更）时被自动计算覆盖。

**同样受影响的字段**：`arrival_voucher`、`acceptance_voucher`、`invoice_date`、`invoice_date_note`、`invoice_status` 等在 `_refresh_project` 中被无条件写入的字段都面临此问题。

### 提示词2 — 项目管理人工修改保护机制
```
在 zfmd.project.management 模型中，新增人工修改保护机制。

方案：为可能被自动计算覆盖的字段增加对应的 manual_override 标记字段。

新增字段：
- execution_status_manual: Boolean(string="手动维护合同执行情况", default=False)
- arrival_voucher_manual: Boolean(string="手动维护到货单", default=False)
- acceptance_voucher_manual: Boolean(string="手动维护验收单", default=False)
- invoice_status_manual: Boolean(string="手动维护发票开具情况", default=False)

逻辑规则（以 contract_execution_status 为例）：
```

```
修改 zfmd.service.record 中 service_end_date 的自动填充逻辑。

def _compute_service_end_date_from_site(self):
    """通过场站名称关联合同台账，取最新的服务结束日期"""
    for record in self:
        if not record.site_name:

            ("site_id.name", "=", record.site_name),
            ("entry_state", "=", "confirmed"),

            record.service_end_date = max(d for d in dates if d) if any(dates) else False

  关联逻辑 → 通过 site_id.name 查找所有匹配的服务记录

⚠️ 数据修复：
```

## 需求九：开票登记 — 新建时选择对应应收计划条目

### 问题分析

用户在开票登记中新建条目时，需要一个步骤来关联对应的应收计划条目。这样：
- 系统能将开票与应收计划建立关联
- 方便追踪哪些应收款项已开票、哪些未开票
- 开票金额和应收金额可以互相校验

### 提示词14 — 开票登记新建时选择应收计划条目
```
在 zfmd.invoice.record 中实现新建开票时选择对应应收计划条目的功能。

设计方案：

1. 在 invoice_record 模型新增字段：
- receivable_plan_id: Many2one("zfmd.receivable.plan", string="关联应收计划")
  用于记录该笔开票对应的应收计划条目

2. 视图设计（invoice_record_views.xml form）：
在 form 视图中新增 receivable_plan_id 字段，放在合同编号之后：
<field name="receivable_plan_id"
       string="对应应收计划条目"
       domain="[('display_contract_no', '=', display_contract_no)]"
       context="{'default_display_contract_no': display_contract_no}"/>

domain 的作用：自动过滤只显示当前合同编号下的应收计划条目。

3. 新建开票时的"选择步骤"设计：
   
   方式一（推荐 — 在 form 中集成）：
   - 用户先选择/输入合同编号(contract_id)
   - receivable_plan_id 字段自动过滤该合同下的应收计划条目
   - 用户从下拉列表中选择对应的应收条目
   - 选择后自动带入该应收条目的信息（应收款项名称、应收金额等参考显示）

   推荐方式一，更简洁，无需额外开发向导。

@api.onchange("receivable_plan_id")
def _onchange_receivable_plan_id(self):
    for record in self:

   新增 compute 字段显示"已开票金额"（汇总关联的 invoice_record 的 invoice_amount）

- tree 视图中新增 receivable_plan_id 列（optional="show"）
- form 视图中新增 receivable_plan_id 字段

⚠️ 导入兼容：

通过 合同编号 + 应收款项名称 自动匹配关联。
```
