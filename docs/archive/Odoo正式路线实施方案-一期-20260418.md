# Odoo 正式路线实施方案（一期）

## 一、项目定位

本系统以 `合同` 为主线，覆盖：

- 合同台账
- 开工申请
- 服务记录
- 开票登记
- 回款登记
- 应收计划

目标不是先做复杂流程，而是先做一套：

- 能完整录入
- 能批量导入
- 能灵活查找
- 能稳定导出与备份
- 能把主要业务数据拉通

一期完成后，再进入分析、流程化查找、采购、工程实施、售后等扩展阶段。

## 二、一期总原则

### 1. 先满足录入和查找
一期优先级最高的是：

- 全量字段支持
- 批量导入稳定
- 手工录入顺畅
- 自定义筛选好用
- 一键导出和备份可用

### 2. 数据拉通以合同为主线，但允许先业务后合同
系统要支持两类真实业务场景：

- 先有合同，再录开工、服务、开票、回款、应收
- 先有开工申请或售后服务单，后续再补合同编号

所以所有业务对象都应支持：

- `已关联合同`
- `待关联合同`

### 3. 所有关键表头都应可查可筛
04-10 表中有价值的字段，原则上都要能成为筛选条件。

### 4. 云上为正式方向，本地为开发与备用环境
后续正式运行以云上为主，但开发调试、本地演示和应急回退都要支持本地部署。

## 三、为什么继续选择 Odoo

在当前阶段，Odoo 继续作为正式路线是可行的，原因如下：

- 20 人以内规模完全能承接
- 用户、权限、菜单、表单、列表、搜索、导入导出这些底座能力现成
- 支持本地和云上双部署
- 后续还可以扩展采购、工程实施、售后流程

但接下来的开发方式必须变化：

- 不再以零散页面补丁为主
- 改为按“底座能力 + 业务对象 + 分析扩展”三层推进

## 四、一期系统架构

## 1. 平台底座层

负责通用能力：

- 用户与权限
- 菜单与界面收口
- 批量导入
- 搜索筛选
- 导出与备份
- 日志与升级策略

## 2. 业务台账层

负责核心对象：

- 客户
- 场站
- 合同
- 开工申请
- 服务记录
- 开票记录
- 回款记录
- 应收计划

## 3. 分析扩展层

负责后续能力：

- 数据看板
- 常用分析视图
- 个性化查询模板
- 流程预警
- 采购、工程、售后扩展

一期先打好前两层，第三层只保留基础看板与少量分析能力。

## 五、一期重点建设的四个底座

## 1. 导入底座

每类台账要有独立导入器：

- 合同导入器
- 开票导入器
- 回款导入器
- 应收导入器
- 开工导入器
- 服务导入器

每个导入器都必须支持：

- 字段映射
- 必填校验
- 数据预览
- 导入结果反馈
- 错误行提示
- 重复数据识别
- 再次导入的幂等更新策略

### 推荐导入顺序

1. `06 销售合同登记台账`
2. `05 销售合同开发票登记台账`
3. `04 销售合同回款登记台账`
4. `09 执行中合同应收款明细台账`
5. `07 开工申请登记台账`
6. `08 数值天气预报服务台账`
7. `10 应收款统计表` 作为统计校验，不作为主录入表

## 2. 查询筛选底座

系统必须支持两类查询：

### 预设筛选

例如：

- 执行中合同
- 超期服务
- 未回款
- 已开票未回款
- 到期应收

### 自定义高级筛选

要求：

- 主要表头字段都能作为条件
- 支持多条件组合
- 支持日期、金额、状态、客户、场站、销售经理等字段组合查询
- 支持模糊搜索和精准筛选并存
- 支持保存常用筛选

重点不是“有几个固定按钮”，而是“用户自己组合条件时好用、清晰、稳定”。

## 3. 关联底座

数据拉通要支持“强关联”和“弱关联”两种模式。

### 强关联

已有合同编号时：

- 直接挂合同
- 自动带出客户、场站、销售经理、产品线、省区、集团等快照信息

### 弱关联

暂时没有合同编号时：

- 先按客户、场站、项目名称、申请单号、服务单号等录入
- 状态标记为 `待关联合同`
- 后续补录合同编号后，再回填关联合同

这项能力是一期开工和服务模块必须补上的重点。

## 4. 备份与导出底座

### 业务层导出

支持：

- 台账一键导出 Excel
- 按筛选结果导出
- 按选中记录导出

### 系统层备份

支持：

- PostgreSQL 备份
- Odoo 文件目录备份
- 本地与云上恢复方案

## 六、一期业务模型调整建议

## 合同

作为主档，保留并补全以下能力：

- 合同编号
- 合同关键号
- 客户
- 场站
- 省区
- 集团
- 产品线
- 销售经理
- 合同金额
- 服务起止日期
- 关联合同统计

## 开工申请

新增或强化：

- 支持无合同先录入
- 支持后补关联合同
- 保留申请编号、客户、场站、项目内容、状态等字段

## 服务记录

新增或强化：

- 支持无合同先录入
- 支持按服务单号、场站、客户、服务时间查找
- 保留超期判断

## 开票记录

要求：

- 支持按合同编号或合同关键号关联
- 导入时要明确识别失败行

## 回款记录

要求：

- 支持按合同编号或客户回款信息关联
- 保留回款方、日期、金额、备注

## 应收计划

要求：

- 支持应收日期、应收项名称、应收金额、实收金额、状态
- 正确区分明细行和汇总行

## 七、权限设计

一期建议至少保留两类账户：

- `admin`
- `zfmd`

但架构上要为后续细分角色留空间。

后续建议可扩展为：

- 超级管理员
- 业务管理员
- 普通录入人员
- 财务人员
- 只读查看人员

当前阶段，先保证：

- `admin` 负责系统维护与升级
- `zfmd` 负责业务录入与查询

## 八、界面策略

一期界面目标不是花哨，而是：

- 业务菜单清晰
- 录入项完整
- 列表页适合查找
- 自定义筛选好用
- 尽量减少 Odoo 技术感

不再依赖人工逐项勾权限，而是把账号、菜单、界面收口固化进模块里。

## 九、部署策略

## 正式方向

以云上部署为主：

- 阿里云服务器
- Docker Compose
- PostgreSQL + Odoo
- 支持后续 HTTPS 和域名

## 开发与备用方向

保留本地部署能力：

- 用于开发调试
- 用于演示和紧急备用
- 用于升级前验证

## 十、客户开始录入数据后的开发原则

客户开始录入数据后，不代表不能继续开发，但开发策略必须更稳。

### 原则

1. 每次升级前先备份数据库
2. 不轻易删除真实业务数据
3. 核心模型结构变更要评估迁移影响
4. 先在本地或测试环境验证，再上云环境

### 当前建议

在一期功能未稳定前，不建议让客户在唯一环境中大量录入正式数据。

可以：

- 少量试录
- 用于验证流程
- 用于确认字段和查询方式

## 十一、一期开发顺序建议

### 阶段 1：导入和字段补齐

- 补齐 04-10 关键字段建模
- 完成 06、05、04、09 的稳定导入
- 完成错误提示和导入预览

### 阶段 2：查询筛选重构

- 补全搜索视图
- 补全高级筛选字段
- 提升自定义筛选可用性
- 保存常用筛选

### 阶段 3：弱关联和后补关联合同

- 开工支持待关联合同
- 服务支持待关联合同
- 补关联合同后自动回填快照字段

### 阶段 4：导出和备份完善

- 按筛选结果导出
- 模块级导出模板
- 数据库备份方案

### 阶段 5：基础看板与统计

- 恢复稳定数据看板
- 合同、开票、回款、应收的基础分析

## 十二、当前建议的正式决策

一句话概括：

`继续以 Odoo 为正式平台，一期优先重构导入、筛选、关联、备份四大底座能力，暂缓复杂流程分析和后续扩展模块。`

这会是当前阶段最稳、最可落地、也最适合你和客户逐步确认需求的路线。
