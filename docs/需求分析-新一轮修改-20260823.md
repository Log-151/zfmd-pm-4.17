# 新一轮修改 — 需求分析与可执行提示词

> 基于用户原始需求，逐条深度分析、完善拆解为可执行的标准开发提示词。
> 日期：2026-08-23

---

## 一、项目现状与本轮结论

本项目是基于 Odoo 17 的单体业务模块 `zfmd_pm`（当前版本 17.0.1.16.0），合同台账（`zfmd.contract`）、开工申请（`zfmd.project.start`）、服务记录（`zfmd.service.record`）、开票登记（`zfmd.invoice.record`）、回款登记（`zfmd.payment.record`）、应收计划（`zfmd.receivable.plan`）、项目管理（`zfmd.project.management`）之间通过合同编号、`contract_id` 以及 `sync_engine` 联动。

本轮六项需求（列求和、状态列下线、负开票金额、列顺序调整、看板刷新、备份权限）总体判断：

| 需求 | 当前实现 | 改造级别 | 主要影响 |
|---|---|---:|---|
| 筛选后列表自动求和 | 回款登记、开票登记已带 `sum`；其余模块无 | 低 | 仅改列表视图 XML |
| 除合同台账外取消状态列 | 开工申请/开票登记/应收计划列表有状态列；服务记录/回款登记/项目管理列表本就没有 | 低 | 列表视图 XML、表单视图、搜索视图（保留） |
| 开票金额可记负数 | 模型支持负数，但 `sync_engine` 计算已开票应收款时 `max(..., 0)` 截断为 0 | 低-中 | sync_engine 公式、历史数据重算 |
| 列顺序手动调整 | 无（Odoo 原生不支持拖拽列序；已有按用户持久化列宽的 JS 先例） | 中 | 新增 JS 补丁，复用列宽补丁模式 |
| 看板-全局概览数据不准确 | 概览 HTML 块为缓存值，仅按钮/联动时刷新，打开页面不刷新 | 低-中 | dashboard 模型方法、视图 |
| 备份中心 access denied | `_check_backup_manager` 权限校验拦截：当前用户不在 `zfmd_pm.group_zfmd_backup_manager` 组 | 低 | 用户组配置，必要时代码兜底 |

## 二、需求一：筛选后列表自动求和

### 2.1 需求理解

对筛选后的某些金额列自动求和，数值显示在列表页面最下方。Odoo 17 原生列表（tree）视图的 `sum="标签文字"` 属性即为该能力：**求和始终针对当前筛选结果**，显示在列表底部合计行，筛选变化时自动重算，无需额外开发。

## 四、需求三：开票金额允许记录为负数

### 4.1 业务含义

开票金额为负 = 未开票、提前回款，即"欠客户发票"。后续补开正数发票后自然冲销。因此"已开票应收款"应按正常数学关系计算：`已开票应收款 = 开票金额合计 − 已回款`，允许为负。

### 4.2 现状与根因

- `zfmd.invoice.record.invoice_amount`（invoice_record.py:53）为普通 `fields.Float`，模型层可存负数，无 `>= 0` 约束，无需改模型。
- **根因**在 sync_engine.py:351：

```python
"invoiced_receivable_amount": max(net_invoice_amount - paid_amount, 0.0),
```

`max(..., 0.0)` 把负值截断为 0，与"正常数学关系"矛盾。同段 `total_receivable_amount`、`actual_total_receivable_amount` 亦有 `max` 截断（合同总额−回款 场景），需按同一业务口径处理。

### 4.3 待确认问题

1. `total_receivable_amount = 合同总额 − 已回款`、`actual_total_receivable_amount = 合同总额 − 已回款 − 坏账` 是否同样允许负数？（提前回款超过合同总额时）建议与已开票应收款口径一致：允许负值，不做截断。
2. 同步引擎（_refresh_project）修正后，需对既有项目管理记录执行一次重算（"按台账重新生成"按钮或一次性脚本），确认要执行。
3. 开票登记表单 `invoice_situation`（已开/部分未开/未开）在负数场景下的取值逻辑是否需要调整（如按净开票金额判断），请指定；默认维持现有判断。

### 提示词3 — 开票金额允许负数并按数学关系计算

```
1. 修改 models/sync_engine.py 的 _refresh_project（约 line 345-355）：
   - invoiced_receivable_amount 改为 net_invoice_amount - paid_amount，去掉 max(..., 0.0)；
   - total_receivable_amount、actual_total_receivable_amount 的 max 截断按同一口径
     处理（保留截断或允许负值，以需求确认结论为准，默认与已开票应收款一致：允许负值）。

2. 全项目搜索对 invoice_amount 的“非负”限制或求和逻辑（如 dashboard、export_mixin），
   核对负数是否被正确计入（求和按数学关系，负数自然抵减）。

3. 修正后对既有项目管理记录重算一次已开票应收款（使用现有“按台账重新生成”按钮
   或等价同步逻辑），验证历史数据与手工预期一致。

4. 验证用例：
   - 某项目已回款 10 万、尚未开票：录入开票金额 -10 万，已开票应收款 = -10 万；
   - 补开 12 万发票后：已开票应收款 = 12 − 10 = 2 万；
   - 看板与导出中该字段按数学关系展示负值，不做 0 截断。
```

## 五、需求四：列顺序手动调整（可行性评估）

### 5.1 评估结论

**需求可实现，且本项目已有安全实现先例。**

- Odoo 17 原生列表视图**不支持拖拽调整列顺序**（列宽调整原生支持，列顺序不支持）。自行实现拖拽需重写 ListRenderer 渲染顺序，风险高（与列宽补丁、聚合行、可选列面板交互复杂），**不推荐**。
- 项目已有 `static/src/js/list_column_width_patch.js`：按"模型 × 用户"用 `localStorage` 持久化列宽、列表挂载时恢复的 OWL patch 模式。列顺序可采用**同一模式**安全实现，且二者可合并为一个补丁。

### 5.2 推荐方案：按点选顺序排序列

用户点选列标题（按点击先后顺序），列表按该顺序重排列。交互设计要点：

- **模式切换**：单机列表标题当前被"排序"占用。提供"调整列序"开关（列表工具条按钮），开启后点击列头进入"记录顺序"模式：依次点选列标题，点完确认后应用并保存；关闭后恢复单机排序。
- **持久化**：`zfmd_pm.list_order.<model>` 按用户存 localStorage（与列宽键同模式）。
- **应用方式**：在 ListRenderer patch 中根据存储顺序对表头 DOM 重排，或对 `list.columns` 重排后重渲染。
- **恢复默认**：提供"恢复默认列序"入口，清除存储即回到 XML 定义顺序。

### 5.3 待确认问题

1. 采用"开关模式 + 点选顺序"交互，还是期望其他交互（如 Ctrl+点击直接记录顺序）？
2. 列顺序按用户本机保存（localStorage）还是要求登录账号跨设备同步（需建模型存储，工作量上升）？默认按本机保存。

### 提示词4 — 列顺序按点选调整

```
参照 static/src/js/list_column_width_patch.js 的 patch 模式，实现 ZFMD 列表列顺序调整：

1. 在列表工具条（ListController 控件区）为 ZFMD_LIST_MODELS 覆盖的模型增加
   “调整列序”切换按钮。开启后：
   - 点击任意列标题不触发排序，改为按点击先后顺序记录列序（被点中的列高亮并显示序号）；
   - 提供“应用”与“取消”按钮；应用后按记录顺序重排列并写入
     localStorage 键 zfmd_pm.list_order.<model>（JSON 数组，元素为列 data-name）；
   - 关闭开关后列头恢复单机排序行为。

2. 列表挂载时读取 zfmd_pm.list_order.<model>，若存在则按该顺序重排列
   （未出现在存储中的列按 XML 原顺序排在末尾）。

3. 提供“恢复默认列序”入口：清除该 localStorage 键并重渲染为 XML 定义顺序。

4. 与现有 list_column_width_patch 兼容：列宽按 data-name 持久化，与顺序无关，
   顺序调整后列宽跟随列而非位置。

5. 验证：多列重排后刷新页面顺序保持；另一个浏览器/用户不受影响；
   恢复默认后回到 XML 顺序；排序、分组、筛选、聚合行功能不受影响。
```

## 六、需求五：数据看板-全局概览数据不准确

### 6.1 现状与根因

- `zfmd.dashboard` 的概览页（page_mode="overview"）内容由 `_refresh_overview_blocks()`（dashboard.py:1374）计算并写入 `overview_metrics_html` / `overview_warning_html` / `overview_shortcuts_html` 三个 Html 字段，属**缓存值**。
- 现有刷新时机：概览页"刷新概览"按钮（action_refresh_overview）、以及部分 create/write 联动（dashboard.py:1636-1652）。
- 业务数据（合同、回款、开票等）变更后，若未触发上述刷新，概览页展示的就是旧值——即"看板数据更新后显示不准确"的根因。页面每次打开**没有自动刷新**。

### 6.2 修复方向

打开概览页时自动重算概览块（幂等、开销可控），并核对概览统计口径与各台账一致。

### 6.3 待确认问题

1. "不准确"是指概览统计值滞后（刷新后即正确），还是刷新后数值仍与台账不一致？若是后者，请提供具体不一致的指标名，便于按口径修正统计逻辑。

### 提示词5 — 全局概览自动刷新与口径核对

```
1. 打开概览页时自动刷新：为 zfmd.dashboard 的概览 form 视图
   （views/dashboard_views.xml 的 view_zfmd_dashboard_overview_form）
   增加打开时调用 action_refresh_overview 的机制（如 onchange 或 act_window 上下文触发），
   或为 action_zfmd_dashboard_overview 增加 context 使进入页面即执行 _refresh_overview_blocks。

2. 刷新保持幂等：多次打开页面重复计算不影响结果；计算开销可控
   （概览块仅一个 dashboard 记录，聚合查询可接受）。

3. 核对概览指标口径与各台账列表一致（合同数、回款、开票、应收、预警等），
   逐项与对应台账的筛选求和结果对比；发现口径不一致的指标，修正其统计查询。

4. 验证：修改一笔回款后进入“全局概览”，指标立即反映新值，无需手工点“刷新概览”。
```

## 七、需求六：备份中心生成系统备份失败 access denied

### 7.1 现状与根因

- `zfmd.backup.record` 的 `create_backup` 流程调用 `_check_backup_manager()`（backup.py:85-91）：

```python
if not (
    self.env.is_superuser()
    or self.env.user.has_group("base.group_system")
    or self.env.user.has_group("zfmd_pm.group_zfmd_backup_manager")
):
    raise AccessError(_("您没有执行备份操作的权限。"))
```

- 触发"access denied"说明当前登录账号：既非超级管理员/系统设置权限，也**不在 `zfmd_pm.group_zfmd_backup_manager` 组**中。security.xml:23 定义了该组，且该组拥有备份记录与备份中心的模型访问权限（ir.model.access.csv:30-31）。
- 另需排查：`_backup_root()`（backup.py:80-83）目录写权限（`config["data_dir"]/backups/zfmd_pm/<db>`）与 pg_dump 可执行权限——权限组配置正确后若仍失败，需看备份记录的 error_message 字段定位（pg_dump 报错会写入 UserError）。

### 7.2 修复方向

1. 运维配置：将使用备份中心的账号加入 `zfmd_pm.group_zfmd_backup_manager` 组（设置 → 用户与公司 → 用户 → 该账号 → 勾选对应组）。若该账号本就应拥有全部权限，检查其用户组配置是否被误删。
2. 代码兜底（可选）：备份中心向导的按钮对无权限用户隐藏/禁用，并给出中文提示，而不是报英文 access denied（需确认实际报错文案来源：Odoo AccessError 或浏览器/代理层）。
3. 权限修好后执行一次系统备份，若仍失败，读取备份记录 error_message 并修复底层问题（目录权限、pg_dump 路径等）。

### 提示词6 — 备份权限修复

```
1. 确认用户组配置：检查当前登录账号是否具有 base.group_system 或
   zfmd_pm.group_zfmd_backup_manager 组；若无，通过“设置→用户”将其加入
   zfmd_pm.group_zfmd_backup_manager 组（并告知运维按此配置账号）。

2. 代码兜底（若需）：备份中心向导（backup_center_wizard_views.xml）中，
```
