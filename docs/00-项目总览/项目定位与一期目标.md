# 项目定位与一期目标

## 一、项目定位

本系统以 `合同` 为主线，覆盖：

- 合同台账
- 开工申请
- 服务记录
- 开票登记
- 回款登记
- 应收计划

目标不是先做复杂流程，而是先做一套：

- 能完整录入
- 能批量导入
- 能灵活查找
- 能稳定导出与备份
- 能把主要业务数据拉通

一期完成后，再进入分析、流程化查找、采购、工程实施、售后等扩展阶段。

## 二、一期模块边界

### 必做

- 合同主档
- 开工申请
- 服务记录
- 开票登记
- 回款登记
- 应收计划
- 多条件筛选
- 基础导出

### 第二批再做

- 自动预警
- 自动统计报表
- Excel 历史数据导入
- 月度汇总
- 复杂审批流

## 三、一期总原则

### 1. 先满足录入和查找

一期优先级最高的是：

- 全量字段支持
- 批量导入稳定
- 手工录入顺畅
- 自定义筛选好用
- 一键导出和备份可用

### 2. 数据拉通

以合同为主线，但允许先业务后合同。系统要支持两类真实业务场景：

- 先有合同，再录开工、服务、开票、回款、应收
- 先有开工申请或售后服务单，后续再补合同编号

所以所有业务对象都应支持：

- `已关联合同`
- `待关联合同`

### 3. 所有关键表头都应可查可筛

04-10 表中有价值的字段，原则上都要能成为筛选条件。

### 4. 云上为正式方向，本地为开发与备用环境

后续正式运行以云上为主，但开发调试、本地演示和应急回退都要支持本地部署。

## 四、为什么继续选择 Odoo

在当前阶段，Odoo 继续作为正式路线是可行的，原因如下：

- 20 人以内规模完全能承接
- 用户、权限、菜单、表单、列表、搜索、导入导出这些底座能力现成
- 支持本地和云上双部署
- 后续还可以扩展采购、工程实施、售后流程

但接下来的开发方式必须变化：

- 不再以零散页面补丁为主
- 改为按"底座能力 + 业务对象 + 分析扩展"三层推进

## 五、一期业务模型调整建议

### 合同

作为主档，保留并补全以下能力：

- 合同编号
- 合同关键号
- 客户
- 场站
- 省区
- 集团
- 产品线
- 销售经理
- 合同金额
- 服务起止日期
- 关联合同统计

### 开工申请

新增或强化：

- 支持无合同先录入
- 支持后补关联合同
- 保留申请编号、客户、场站、项目内容、状态等字段

### 服务记录

新增或强化：

- 支持无合同先录入
- 支持按服务单号、场站、客户、服务时间查找
- 保留超期判断

### 开票记录

要求：

- 支持按合同编号或合同关键号关联
- 导入时要明确识别失败行

### 回款记录

要求：

- 支持按合同编号或客户回款信息关联
- 保留回款方、日期、金额、备注

### 应收计划

要求：

- 支持应收日期、应收项名称、应收金额、实收金额、状态
- 正确区分明细行和汇总行

## 六、权限设计

一期建议至少保留两类账户：

- `admin`
- `zfmd`

但架构上要为后续细分角色留空间。

后续建议可扩展为：

- 超级管理员
- 业务管理员
- 普通录入人员
- 财务人员
- 只读查看人员

当前阶段，先保证：

- `admin` 负责系统维护与升级
- `zfmd` 负责业务录入与查询

## 七、界面策略

一期界面目标不是花哨，而是：

- 业务菜单清晰
- 录入项完整
- 列表页适合查找
- 自定义筛选好用
- 尽量减少 Odoo 技术感

不再依赖人工逐项勾权限，而是把账号、菜单、界面收口固化进模块里。

## 八、客户开始录入数据后的开发原则

客户开始录入数据后，不代表不能继续开发，但开发策略必须更稳。

### 原则

1. 每次升级前先备份数据库
2. 不轻易删除真实业务数据
3. 核心模型结构变更要评估迁移影响
4. 先在本地或测试环境验证，再上云环境

### 当前建议

在一期功能未稳定前，不建议让客户在唯一环境中大量录入正式数据。

可以：

- 少量试录
- 用于验证流程
- 用于确认字段和查询方式

## 九、当前假设

- Odoo 版本按 `17 Community` 先搭建
- 当前先做一个主模块 `zfmd_pm`
- 后续如果功能继续扩大，再拆子模块

## 十、一句话概括

继续以 Odoo 为正式平台，一期优先重构导入、筛选、关联、备份四大底座能力，暂缓复杂流程分析和后续扩展模块。

这会是当前阶段最稳、最可落地、也最适合和客户逐步确认需求的路线。
