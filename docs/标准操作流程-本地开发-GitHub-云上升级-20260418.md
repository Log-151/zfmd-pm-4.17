# 标准操作流程：本地开发 -> GitHub -> 云上升级

## 一、目的

从现在开始，项目统一采用下面的工作方式：

- `本地环境`：开发、调试、验证
- `GitHub`：代码版本管理与阶段性发布中转
- `云上环境`：阶段性演示、客户查看、后续正式部署

这样做的目标是：

- 降低云上反复试错风险
- 先在本地把功能跑顺
- 保证每次上云都是相对稳定版本
- 方便后续备份、回滚和多人协作

## 二、环境分工

## 1. 本地环境

用途：

- 新功能开发
- 改字段和页面
- 跑模块升级
- 测试导入、筛选、导出
- 看日志排查问题

原则：

- 所有新需求先在本地验证
- 没在本地跑通的功能，不直接上云

## 2. GitHub

用途：

- 作为代码中转站
- 记录每次阶段性稳定版本
- 让云服务器能统一拉取最新代码

原则：

- 只有本地验证通过后才推送
- 提交说明尽量清楚

## 3. 云上环境

用途：

- 演示给客户看
- 验证云服务器环境表现
- 阶段性发布

原则：

- 不在云上直接做开发主操作
- 云上只接收“本地验证通过”的阶段版本

## 三、标准执行顺序

## 步骤 1：先在本地开发

每次开发都先在本地完成：

- 改代码
- 本地升级模块
- 本地验证页面、导入、筛选、导出

本地常用动作：

```bash
docker restart zfmd_odoo
docker exec zfmd_odoo odoo -d zfmd_pm -u zfmd_pm --stop-after-init
docker logs --tail 80 zfmd_odoo
```

## 步骤 2：本地验证通过后提交 Git

当本地验证通过后，再执行：

```bash
git add .
git commit -m "本次改动说明"
git push
```

要求：

- 每次提交说明尽量写清楚改了什么
- 不要把明显未完成、未验证的半成品直接推上云

## 步骤 3：云服务器拉代码

在云服务器执行：

```bash
cd /opt/zfmd-pm-4.17
sudo git pull
```

## 步骤 4：云上升级模块

在云服务器执行：

```bash
cd /opt/zfmd-pm-4.17
sudo docker compose restart odoo
sudo docker compose exec odoo odoo -d zfmd_pm -u zfmd_pm --stop-after-init
```

## 步骤 5：云上回归检查

升级完成后，至少检查以下内容：

- `admin` 能否登录
- `zfmd` 能否登录
- 主要菜单能否打开
- 新功能是否正常
- 导入、筛选、导出是否正常

## 四、每次升级前的检查项

在推 GitHub 之前，先确认：

- 本地模块升级通过
- 没有明显报错
- 功能路径已经验证
- 如果涉及导入，至少试跑一遍
- 如果涉及权限，至少用 `zfmd` 看一遍

## 五、每次云上升级后的检查项

建议固定检查：

1. 登录页是否正常
2. `zfmd` 界面是否正常
3. 菜单和页面是否能打开
4. 导入入口是否可用
5. 列表筛选是否正常
6. 导出是否可用

## 六、什么时候不应该立刻上云

以下情况建议先留在本地，不要马上部署到云上：

- 新需求还没完全理解
- 功能刚改完，还没本地验证
- 涉及核心模型结构变更
- 涉及批量导入逻辑重构
- 涉及权限、菜单、品牌化大改

## 七、如果云上已经有客户试用数据

当云上开始出现客户真实录入数据后，执行以下原则：

### 1. 升级前先备份数据库

### 2. 大改字段结构前先评估影响

### 3. 先在本地验证通过，再上云

### 4. 尽量避免在云上直接做实验性修改

## 八、建议的工作节奏

后续建议统一按这个节奏推进：

### 日常节奏

1. 本地开发
2. 本地验证
3. 推 GitHub
4. 云上升级
5. 云上检查

### 功能节奏

1. 先做一小块
2. 跑通一小块
3. 再推下一小块

不要一次改太大，再一起上云。

## 九、当前阶段的推荐实践

当前项目还处于一期底座能力建设阶段，所以推荐：

- 本地作为主开发环境
- 云上作为阶段性发布环境
- 客户看云上
- 开发和排错主要在本地

## 十、当前统一口径

一句话概括：

`以后所有新需求，先在本地开发验证，再推 GitHub，最后阶段性升级到云上。`
